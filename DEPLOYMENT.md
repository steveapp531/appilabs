# Deployment

Target setup: **frontend, Express API and scheduled Python reports as Vercel Services**, **database on MongoDB Atlas**, **uploads on Cloudflare R2** (or any private S3-compatible bucket).

The frontend and API share one domain. Vercel routes `/api/*` to the backend, and the automation service reaches the backend through an internal service binding. This keeps admin cookies first-party and avoids browser CORS between the frontend and API.

## 1. MongoDB Atlas

1. Create a project and a cluster (M0 free is fine to start; M10+ adds automated backups).
2. **Database Access:** create a user with read and write access to the `appilabs` database only.
3. **Network Access:** allow Vercel's outbound connections. If your Vercel plan supports static outbound IPs, allowlist those. Otherwise, Atlas may need `0.0.0.0/0`; use a strong database password and a database user restricted to the AppiLabs database.
4. **Connect > Drivers:** copy the URI and add the database name:
   `mongodb+srv://USER:PASS@cluster0.xxxxx.mongodb.net/appilabs?retryWrites=true&w=majority`

## 2. Object storage (Cloudflare R2)

1. Create a bucket such as `appilabs-uploads`. Leave public access **off**.
2. Create an API token with Object Read and Write on that bucket.
3. Note the account endpoint `https://<account-id>.r2.cloudflarestorage.com`, access key and secret.

## 3. Vercel Services

1. Vercel > **Add New > Project** > import the GitHub repository. Leave **Root Directory** at the repository root so Vercel reads the root `vercel.json` and builds all three services.
2. Add the environment variables below in **Settings > Environment Variables**. Use separate production and preview databases/credentials. The `APPILABS_API_URL` binding is generated by Vercel; do not create a variable with that name yourself.

| Service | Variable | Value |
| --- | --- | --- |
| Backend | `NODE_ENV` | `production` |
| Backend | `MONGODB_URI` | Atlas URI from step 1 |
| Backend | `JWT_SECRET` | Random secret with at least 32 characters |
| Backend | `PUBLIC_SITE_URL`, `API_PUBLIC_URL` | Your Vercel site origin, e.g. `https://appilabs.com` |
| Backend | `CORS_ORIGINS` | Your Vercel site origin; add the preview origin while testing previews |
| Backend | `COOKIE_SECURE` | `true` |
| Backend | `SETUP_TOKEN` | Long random one-time value; remove after creating the owner |
| Backend | `EMAIL_DRIVER`, `EMAIL_FROM`, `ADMIN_NOTIFY_EMAIL`, `SMTP_*` | Configure `EMAIL_DRIVER=smtp` and credentials from your email provider |
| Backend | `PAYMENT_PROVIDER` | `none` until ready, or `paystack` with a test key |
| Backend | `PAYSTACK_SECRET_KEY` | Paystack test/live secret, when enabled |
| Backend | `STORAGE_DRIVER` | `s3` |
| Backend | `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Values from step 2 |
| Backend | `AUTOMATION_API_KEY` | Long random secret for the automation API |
| Automation | `APPILABS_AUTOMATION_API_KEY` | Same value as backend `AUTOMATION_API_KEY` |
| Automation | `CRON_SECRET` | Long random secret; Vercel Cron sends it as a bearer token |
| Automation | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, `REPORT_TO` | SMTP credentials and internal report recipient |
| Frontend | `VITE_SITE_URL` | Your Vercel site origin, e.g. `https://appilabs.com` |
| Frontend | `VITE_GA_MEASUREMENT_ID` | `G-XXXXXXX` (optional) |
| Frontend | `VITE_GSC_VERIFICATION` | Search Console HTML tag content (optional) |

The browser uses same-origin `/api/v1` requests, which Vercel routes to the backend. Leave `VITE_API_URL` unset (or empty) for this setup. `VITE_SITE_URL` and other `VITE_*` values are embedded at build time, so redeploy after changing them.

3. Deploy. Check `/api/v1/health` and `/api/v1/ready`; the latter should report `"database": "ok"`. Backend migrations run on the first database-backed API request.
4. Use `/admin` with the `SETUP_TOKEN` to create the owner, then remove `SETUP_TOKEN` from Vercel. Seed the catalogue against the production database from a trusted machine with the backend dependencies installed; do not use `--demo` in production.
5. Vercel Cron runs the reports and expired-upload cleanup daily at 07:00 UTC. Trigger `/api/cron/reports` from the Vercel Cron dashboard to test. Check the automation function logs and confirm the email arrives.
6. Add your custom domain under Vercel **Settings > Domains** and follow its DNS instructions. Set `PUBLIC_SITE_URL`, `API_PUBLIC_URL`, `CORS_ORIGINS`, and `VITE_SITE_URL` to that origin, then redeploy.
7. **Deploy hook (optional):** create a Vercel Deploy Hook for `main` and set `VERCEL_DEPLOY_HOOK_URL` on the backend to rebuild prerendered pages after published content changes.

The backend uses serverless functions on Vercel, so uploaded files must use S3-compatible storage; local disk is ephemeral. Vercel function request-size limits also constrain multipart uploads; if uploads exceed the platform limit, use direct-to-object-storage uploads or reduce the configured upload size.

`render.yaml` is retained as an alternative deployment blueprint. Do not deploy both production backends/report schedules against the same database.

## 4. Paystack

1. Dashboard > Settings > API Keys and Webhooks.
2. Webhook URL: `https://appilabs.com/api/v1/payments/webhook/paystack`
3. Callback URL: `https://appilabs.com/payment/callback`
4. Enroll in a course with a test card. Confirm: redirect to Paystack, return to "Payment confirmed", enrollment *Paid* in the admin, payment listed under Payments.
5. Switch to the live secret key only after this succeeds.

## 5. Search and analytics

1. Google Search Console: add the domain property, verify (DNS or `VITE_GSC_VERIFICATION`), submit `https://appilabs.com/sitemap.xml`.
2. Google Analytics 4: create a web stream, set `VITE_GA_MEASUREMENT_ID`, redeploy. Mark `form_submit`, `consultation_request` and `payment_success` as key events.
3. Google Business Profile: create a profile for AppiLabs in Accra with the same name, phone and website URL used in Admin > Settings.

## 6. Backups

- Atlas M10+: continuous backups are built in. Enable them.
- Atlas M0: run a scheduled `mongodump` (for example from a GitHub Action or a small machine) and store the archive in your R2 bucket:
  ```bash
  mongodump --uri "$MONGODB_URI" --archive=appilabs-$(date +%F).gz --gzip
  ```
- Test a restore into a separate database at least once: `mongorestore --uri "$TEST_URI" --archive=file.gz --gzip`.

## Deployment checklist

### Staging

- [ ] Separate Atlas database (for example `appilabs_staging`) and separate R2 bucket
- [ ] `PAYMENT_PROVIDER=paystack` with a **test** key, or `mock` on staging only
- [ ] `npm run seed -- --demo` allowed on staging only
- [ ] All flows tested: start a project (with file), contact, booking, enrollment and payment, research request (with file), resource download, newsletter confirmation email
- [ ] Admin: sign in, change a lead status, export CSV, download an uploaded file, edit and publish an article
- [ ] Python report job run manually and received by email
- [ ] `/api/v1/ready` healthy; Lighthouse run on home, a service page and a course page

### Production

- [ ] `NODE_ENV=production`, `COOKIE_SECURE=true`, strong `JWT_SECRET`
- [ ] `CORS_ORIGINS` and `PUBLIC_SITE_URL` match the real domains
- [ ] `STORAGE_DRIVER=s3` with a private bucket
- [ ] `EMAIL_DRIVER=smtp` with SPF, DKIM and DMARC records configured for the sending domain
- [ ] `PAYMENT_PROVIDER=paystack` with the live key and webhook, or `none`
- [ ] Owner account created; `SETUP_TOKEN` removed
- [ ] Admin > Settings: real email, phone, WhatsApp, address, service areas, social links
- [ ] Demo prices confirmed or changed; *Demo price* flags removed
- [ ] Sample articles and illustrative case studies replaced or unpublished
- [ ] Founder bio checked in `shared/content/site.js`
- [ ] Privacy policy and terms reviewed by a lawyer
- [ ] Sitemap submitted; GA4 receiving events
- [ ] Backups enabled and a restore tested
- [ ] Uptime monitor on `/api/v1/health` (for example UptimeRobot or Better Stack)
